# zemon-mcp — MCP Server Wrapping (issue #12)

**Date:** 2026-07-16
**Scope:** GitHub issue #12 (MCP server wrapping / `zemon-mcp`)
**Goal:** Expose the `zemon` monitoring/debugging surface to AI agents as a Model Context
Protocol (MCP) server — a thin, tokio-based adapter over the existing `zemon-core` library
— so agents interact via structured tool calls instead of parsing CLI text.

This document fixes the design agreed during brainstorming. Implementation follows in a
separate plan (`writing-plans`). Building the crate is the follow-up step, not part of this
spec.

---

## Motivation

If the primary user of `zemon` is an AI agent, an MCP server is more agent-native than a
CLI: tool schemas and structured I/O are guaranteed at the protocol level, so an agent
issues a typed tool call and receives typed data rather than parsing text.

The precondition named in #12 — "harden the CLI contract first (P0 bounding, P1 JSON
errors/envelope)" — is now met: bounded commands, the `{count, items}` envelope, NDJSON
streaming, structured `ZemonError` with stable exit codes, and unit-testable command logic
all landed via the CLI-agent-ergonomics stack (PR #51) and config resolution (PR #32).
`zemon-core` is already a shared, tokio-based library, so the MCP server is a thin adapter
that reuses the same core functions and the same serde output types as the CLI's `--json`
mode.

## Key decisions (from brainstorming)

1. **Deliverable:** design spec + implementation plan now; implementation is a follow-up
   after plan approval.
2. **Streaming boundary:** bounded-snapshot tools. `sub`/`nodes watch` become finite tools
   that collect for `count`/`duration` then return a batch. No server-push streaming in v1.
3. **Session model:** one persistent, lazily-initialized, reconnecting Zenoh session reused
   across all tool calls (the server binds to a single network for its lifetime).
4. **Tool set:** read-only tools + `pub` (test injection). Excludes `queryable serve`,
   `capture`/`replay`, `tui`.
5. **Packaging:** a `zemon-mcp` **library** crate (the adapter) driven by a new
   `zemon mcp` **subcommand** in the existing `zemon` binary — preserves the "single binary"
   convention (CLAUDE.md) while keeping the MCP logic an isolated thin crate.
6. **Transport:** stdio (the standard local-MCP transport used by Claude Desktop/Code).
7. **SDK:** `rmcp` + `rmcp-macros` (the official Rust MCP SDK, tokio-based).

## Architecture

```
crates/
  zemon-core/   # unchanged shared library (session, discover, query, scout, doctor, …)
  zemon-mcp/    # NEW library crate: rmcp server + tool handlers over zemon-core
  zemon-cli/    # gains a `zemon mcp` subcommand that constructs config + runs zemon-mcp
  zemon-tui/    # unchanged
```

- `zemon-cli`'s `Command::Mcp` resolves configuration through the existing
  `resolve_config` (PR #32) using the same global flags (`-e`, `-m`, `-c`, `--scout-port`,
  `--connect-timeout`, `ZEMON_*`), then hands the resolved `ZemonConfig` to
  `zemon_mcp::serve_stdio(config).await`.
- `zemon-mcp` owns only: MCP server wiring, tool input/output types, session lifecycle, and
  the mapping from `zemon-core` results/errors to MCP tool results. It contains no Zenoh
  protocol logic of its own.

### Components (`zemon-mcp`)

- **`ServerState`** — holds the resolved `ZemonConfig` and a lazily-opened, reconnecting
  session: `Arc<Mutex<Option<Session>>>`. A `session()` accessor opens the session on first
  use and re-opens it if a prior call observed a dropped connection (mirrors the TUI's
  non-blocking reconnection pattern; network calls never block the protocol loop
  indefinitely — each tool honors its own timeout).
- **Tool handlers** — one thin async fn per tool. Each obtains `state.session()` (except the
  pure tools), calls the corresponding `zemon-core` function, and returns a value serialized
  with the **same serde types the CLI uses** (e.g. `output::to_collection_json`,
  `TopicInfo`, `NodeInfo`, `ZenohMessage`). Pure tools (`keyexpr`, `config_show`) never touch
  the session.
- **Tool schemas** — generated by `#[tool]` / `rmcp-macros` from typed input structs, so the
  JSON schema advertised to the agent is derived from Rust types.
- **Transport** — stdio via rmcp's stdio server entry point.

## Tool set (v1)

Read tools (reuse existing core functions):

| Tool | Inputs | Core call | Session |
|------|--------|-----------|---------|
| `discover` | `key_expr="**"` | `discover::discover` | yes |
| `query` | `key_expr`, `payload?`, `timeout="5s"`, `limit?` | `query::get` | yes |
| `nodes` | — | `registry::query_admin_nodes` (+ scout merge as in CLI) | yes |
| `liveliness` | `key_expr="**"` | `discover::query_liveliness` | yes |
| `scout` | `port_range?`, `per_port_timeout?` | `scout` | yes (transient) |
| `doctor` | `timeout?` | `doctor::run` | yes |
| `keyexpr` | `a`, `b` | `keyexpr` | **no (pure)** |
| `info` | — | `info` | yes |
| `config_show` | — | `resolve_config` | **no (pure)** |
| `sub_snapshot` | `key_expr`, `count?`, `duration?`, `max_payload_bytes?` | bounded `subscribe` | yes |

Write tool:

| Tool | Inputs | Core call | Session |
|------|--------|-----------|---------|
| `pub` | `key_expr`, `value`, `att?` | publish | yes (write) |

Excluded in v1 (rationale): `queryable serve` (long-lived daemon), `capture`/`replay`
(file I/O side effects), `tui` (interactive). These can be revisited if needed; excluding
them keeps v1 a clean request/response surface.

### Bounded snapshot semantics

`sub_snapshot` reuses the merged bounded-subscribe logic: it collects messages until
`count` is reached or `duration` elapses (at least one bound required, matching the CLI's
`--watch` guard rails), applies `max_payload_bytes` capping, and returns `{count, items}`.
It is a finite call — there is no server-initiated push. `nodes` returns a single snapshot;
a bounded `nodes_watch` (change diffs over a duration) is a candidate for a later iteration,
not v1.

## Data flow

```
agent → MCP client → stdio → rmcp server → tool handler
        → ServerState.session()  (lazy open / reconnect on drop)
        → zemon-core fn
        → serde-serialized result  (identical shape to CLI --json)
        → agent
```

Reusing the CLI's serde types means the MCP tool responses and the CLI `--json` output stay
byte-for-byte consistent for the same operation, so there is one contract to maintain.

## Error handling

`zemon-core` fns return `ZemonError` (kind + message + stable exit code) or
`color_eyre::Report`. Tool handlers map these to an rmcp tool error carrying the human
message plus structured data `{ "kind": "<invalid_input|connection|timeout|not_found|
internal>" }`, so the agent sees the same error taxonomy the CLI exposes. A tool never
panics the server; a per-call failure is a tool error, and a dropped session is retried once
on the next call before surfacing a `connection` error.

## Configuration

The `zemon mcp` subcommand resolves configuration exactly like every other command, through
`resolve_config(ConfigOverrides { … })` (PR #32). The server therefore honors `ZEMON_*` env
vars, `--config`, `--endpoint`, `--mode`, `--scout-port`, and `--connect-timeout`, and binds
to the single resolved network for its lifetime. `config_show` exposes the same effective
view (allow-listed; no raw Zenoh config / secrets).

## Testing

- **Schema / serialization unit tests** — assert each tool's input struct produces the
  expected JSON schema and each output serializes to the CLI-equivalent shape.
- **In-memory protocol tests** — drive the server over rmcp's in-memory duplex transport and
  assert tool discovery + call/response for the **pure** tools (`keyexpr`, `config_show`),
  which need no zenohd.
- **Session-dependent integration** — exercise `discover`/`query`/`nodes`/`sub_snapshot`/
  `pub` against a local `zenohd` (the existing manual-test path), plus reuse `zemon-core`'s
  own tests for the underlying functions.
- **Error mapping** — assert `ZemonError` kinds map to the documented MCP error data.

## Out of scope (v1)

- Server-push / live streaming via MCP resource subscriptions.
- `queryable serve`, `capture`, `replay`, `tui` tools.
- Multi-network / per-call endpoint switching (the server binds one network per process).
- HTTP/SSE transport (stdio only).

## Delivery

Single implementation plan produces the `zemon-mcp` crate + the `zemon mcp` subcommand,
verified by the tests above and a manual smoke test (launch `zemon mcp`, list tools, call
`keyexpr`/`config_show` with no network, and `discover`/`query` against a local `zenohd`).
